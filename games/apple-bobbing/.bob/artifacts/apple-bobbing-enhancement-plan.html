🍎 Apple Bobbing — Enhancement Plan

4-phase implementation plan · Sound, Leaderboard & Quick Fire Round

⚠ Important Architectural Note

The entire game logic is compiled into a single minified bundle (assets/index-DbgJ57FT.js). The original source code is not present in this repository. All new features must be implemented as an overlay layer written in a separate script file, communicating with the existing game via DOM events and DOM observation (e.g. MutationObserver on score elements, class changes on the quiz card). The bundle itself will not be modified. This is fully achievable but is the key architectural constraint all phases are designed around.

🙋 Requests for Clarity Before Implementation

  1. Leaderboard persistence: Should the leaderboard persist across browser sessions (using localStorage), or is it acceptable for it to reset when the tab is closed? And should it be purely local (one device only) or shared across multiple players on different machines?
  2. Quick Fire Round trigger: When exactly does the Quick Fire Round start — automatically after all 12 regular apples are answered, at a random point mid-game, or triggered manually by a button?
  3. Quick Fire word list: You mention "a storage word needs to be unscrambled." Should I use IBM storage product/feature names as the word bank (e.g. FLASHSYSTEM, DEFENDER, CEPH), or do you have a specific list of words you'd like to provide?
  4. Quick Fire point value: What is the base point value for the Quick Fire round (before the double/triple multipliers)? For example, is it the same as a regular correct answer, a flat 100 pts, or something else?
  5. Multiple Quick Fire rounds: Can the Quick Fire Round occur more than once per game session, or is it a single one-shot round?
  6. Audio files: Do you have specific audio files (mp3/ogg) you'd like to use for the soundtrack and sound effects, or should I generate the correct/wrong tones programmatically using the Web Audio API (no files needed)?
Phase 1 Audio Foundation — Background Soundtrack & Sound Effects ~2–4 hrs · No dependencies

Introduce all audio using the Web Audio API. No external audio files are required — all three sounds are synthesised programmatically (a looping Halloween ambient drone for the soundtrack; a cheerful chime for correct answers; a buzzer/thud for wrong answers). This keeps the project self-contained with zero new asset downloads.

1a. Audio Engine Module New file: audio.js
  • Create audio.js as a plain ES module injected via a <script type="module"> tag in index.html.
  • Initialise a single shared AudioContext on the first user interaction (tap/click) to satisfy browser autoplay policy.
  • Export three functions: playCorrect(), playWrong(), startMusic() / stopMusic().
  • All sounds use OscillatorNode, GainNode, and optionally BiquadFilterNode — no file loading required.
1b. Halloween Background Soundtrack Synthesised
  • A slowly evolving low-frequency drone (2–3 oscillators detuned slightly, filtered through a low-pass) creates ambient Halloween atmosphere.
  • Volume set to roughly 15% master gain — present but never intrusive.
  • Starts when the first apple is tapped (game begins), pauses on game-over, resumes on replay.
  • A muted 🔊/🔇 toggle button is added to the HUD so players can silence it easily.
1c. Correct Answer Sound Synthesised chime
  • A short ascending two-note chime (e.g. C5 → E5, ~250ms each, sine wave with quick decay envelope).
  • Triggered by detecting the correct CSS class applied to an answer button by the existing game engine (via MutationObserver on #quiz-answers).
1d. Wrong Answer Sound Synthesised buzz
  • A low descending buzz (sawtooth wave, ~300ms, pitch drops from 220Hz to 80Hz) — unmistakable "wrong" feedback.
  • Triggered by detecting the wrong (or equivalent) CSS class on an answer button via the same MutationObserver.
  • Clarification needed: The exact class name the bundle applies to wrong answers must be confirmed by inspecting the CSS file or live browser DevTools before implementing.
Phase 2 Leaderboard — Name Entry & Ranked High Scores ~3–5 hrs · Depends on: Phase 1 (AudioContext exists for fanfare)

A leaderboard overlay is shown on the game-over screen. The player enters their name, their score is saved to localStorage (persistent across sessions, single-device by default), and the top 10 scores are displayed ranked by points. A brief fanfare sound plays when a new high score is set.

2a. Score Capture DOM Observer
  • When the #game-over-card element becomes visible (loses the hidden class), read the final score from #game-over-score inner text.
  • This requires no modification to the bundle — the existing DOM element is the source of truth.
2b. Name Entry UI New HTML injected into game-over-card
  • Inject a text input + "Save Score" button into #game-over-card when game-over is detected.
  • Input is pre-focused for keyboard users; a character limit of 20 is enforced.
  • If the player has entered their name before, pre-fill from localStorage.
2c. Leaderboard Storage & Display localStorage
  • Scores stored in localStorage as a JSON array: [{name, score, date}], capped at 20 entries, sorted descending by score.
  • Top 10 rendered as a styled ordered list replacing / augmenting the existing #game-over-scores element.
  • The current player's row is highlighted so they can see where they rank.
  • A "Clear Board" button available for resetting (behind a confirmation step).
2d. New High Score Fanfare Audio
  • If the submitted score ranks #1 on the board, a short ascending fanfare (5-note chime) plays using the Phase 1 audio engine.
  • A "🏆 New High Score!" banner briefly appears above the leaderboard.
Phase 3 Quick Fire Round — Word Unscramble Under 60 Seconds ~5–8 hrs · Most complex phase · Depends on: Phase 1 (audio)

A completely new game mode injected as a full-screen overlay on top of the 3D scene. The cauldron background visually shifts orange. A scrambled IBM storage word is displayed; the player types or taps letters to unscramble it. Triple points for ≤10 s, double for ≤20 s, standard for ≤60 s. Fails if time runs out. This phase has the most open questions (see Clarifications box above).

3a. Orange Visual Shift CSS overlay
  • A full-viewport <div id="quickfire-overlay"> with a semi-transparent orange tint (rgba(255, 100, 0, 0.18)) placed above the canvas but below the HUD.
  • The existing #hud background and counter elements are temporarily hidden so the Quick Fire card takes full focus.
  • An orange pulsing border or glow effect on the card reinforces urgency.
3b. Word Bank & Scrambler Data
  • A curated word list of IBM storage product / feature names (e.g. FLASHSYSTEM, DEFENDER, STORAGEONE, CEPH, VERSASTACK, SPECTRUM, SAFEGUARDED). Final list subject to your approval — see Clarification #3.
  • Words are scrambled using a Fisher-Yates shuffle of the letters. The scrambler guarantees the scrambled form never matches the original word.
  • Each word is used at most once per session.
3c. Unscramble UI New HTML card
  • A centred card shows: "QUICK FIRE!" heading, the scrambled word in large spaced letters, a 60-second countdown timer (colour shifts red below 10 s), and a text input for the player's answer.
  • On mobile: a row of tappable scrambled letter tiles are rendered for drag-and-rearrange interaction (a simpler text-input fallback is always available).
  • On correct submission, the card shows the answer + points earned with a 1.5 s celebration pause before dismissing.
  • On timeout/wrong, a "Time's up!" message is shown, the round ends with 0 pts.
3d. Points Multiplier Logic Game logic
  • ≤10 s remaining used: 3× base points
  • ≤20 s remaining used: 2× base points
  • ≤60 s remaining used: 1× base points
  • Base point value to be confirmed (see Clarification #4). Tentative default: 150 pts base → up to 450 pts.
  • Points are added by directly mutating #score inner text and the same score variable used by the leaderboard, since the bundle's internal score state cannot be patched.
  • Risk: The bundle may overwrite the #score DOM element on its own tick. A strategy of storing the QF points separately and adding them at the moment of game-over score capture is the safest approach.
3e. Round Trigger & Integration Lifecycle
  • Trigger point determined by Clarification #2. Tentative default: automatically triggered when the last apple (12th) is answered.
  • The existing game is paused visually (pointer events disabled on the canvas) during the Quick Fire round.
  • After completion or timeout, normal game-over flow continues.
Phase 4 Polish, Integration Testing & QA ~2–3 hrs · Depends on: Phases 1–3

End-to-end testing of all features together, mobile/touch QA, edge-case handling, and final cosmetic adjustments.

4a. Mobile & Touch Testing
  • Verify audio starts correctly on iOS/Android (requires user gesture; autoplay rules are stricter on Safari).
  • Test leaderboard name input on mobile soft keyboard — ensure it doesn't obscure the UI.
  • Test Quick Fire letter-tile drag interface on small screens.
4b. Edge Cases
  • Player submits no name → score saved as "Anonymous".
  • Player wins Quick Fire with exactly 10 s or 20 s elapsed → boundary conditions for multiplier.
  • Scrambled word is accidentally already correct on first shuffle → re-shuffle until distinct.
  • Audio context suspended mid-game (tab backgrounded) → graceful resume on refocus.
4c. Accessibility
  • All new interactive elements have aria-label attributes.
  • Correct/wrong audio feedback does not replace visual feedback (both are present).
  • Mute button state is preserved in localStorage across sessions.
